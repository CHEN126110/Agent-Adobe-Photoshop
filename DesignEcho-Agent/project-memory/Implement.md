# Implement

## 执行手册

每次处理中大型任务，按这个顺序工作：

1. 先看 `README.md`
2. 再看 `Prompt.md`
3. 再看 `CurrentTask.md`
4. 再看 `../docs/documentation-governance.md`
5. 再看 `../docs/design-agent-operating-system.md`
6. 再看 `Plan.md`
7. 再看 `Status.md`
8. 如需做能力分类，再看 `../docs/agent-capability-map.md`
9. 如需继续实现或排期，再看 `Intake.md` 与 `Backlog.md`
10. 如需判断风险或边界，再看 `Risks.md` 与 `Decisions.md`

## 需求对齐规则

中大型任务开始前必须写或更新 `CurrentTask.md`，至少包含：

1. 用户原始需求
2. 必须做
3. 禁止做
4. 归属层级
5. 当前计划
6. 验收证据

如果用户明确要求某事项“加入规划 / 纳入规划 / 后续要做 / 不要遗忘”，必须写入 `Intake.md`。

禁止只在最终回复里承诺“已纳入规划”，但不写入项目记忆。

## 真实性规则

任何结论只能落入以下四类之一：

1. `已核实（代码）`
2. `已核实（构建）`
3. `已核实（手测）`
4. `未核实 / 待验证`

禁止写法：

- “应该已经可以”
- “理论上没问题”
- “大概率完成”

如果只能推断，必须明确写成“推断”。

## 文档更新规则

以下情况必须更新 `Status.md`：

1. 当前主线改变
2. 代码能力边界发生变化
3. 构建或手测结论变化
4. 发现新的系统性风险
5. 里程碑状态变化

以下情况必须更新 `Backlog.md`：

1. 新增阶段性任务
2. 删除不再成立的任务
3. 任务优先级改变

以下情况必须更新 `Decisions.md`：

1. 明确采用一个方案
2. 明确放弃一个方案
3. 调整架构边界

## 执行规则

1. 优先修根因，不加掩盖层。
2. 优先收真相源，不制造第二份配置。
3. 普通用户链路和内部调试链路必须硬隔离。
4. 如果某项能力还没有手测，不得在状态文件里写成“稳定可用”。
5. 如果某项能力只在单一 case 下有效，不得外推成通用能力。
6. 每次下一步规划必须能追溯到 `CurrentTask.md`、`Intake.md`、`Backlog.md` 或明确的风险项。
7. benchmark 不能进入 skill / MCP / tool 边界；benchmark 只能验证能力点。
8. 业务场景不能定义底层工具真相源；底层能力必须回到能力地图。
9. 默认不要从 `docs` 目录中的研究、复盘、借鉴或专项计划文档直接进入实现；是否可读、是否可作为当前依据，先按 `documentation-governance.md` 判断。

## 验证规则

至少做：

1. 与本次改动直接相关的代码核查
2. 与本次改动直接相关的构建验证

如涉及用户可见主链：

3. 明确标记是否已手测

如涉及规划、项目记忆或方法论：

4. 必须运行 `npm run maintenance:validate`

## 本项目当前特别注意事项

1. 仓库当前存在多类未收口改动，不能随意重置、清理或混合提交。
2. PowerShell 存在中文输出乱码风险，读写文件必须显式使用 UTF-8。
3. 当前关于“设计能力”的很多讨论仍属于方向判断，不能写成项目事实。
